# 维护功能验收清单

维护 `Game/Docs/功能验收清单.md`（Game 工作目录下为 `Docs/功能验收清单.md`），供用户逐项核对当前已实现的玩法规则。

## 范围与格式

- 按玩法系统分组，每个验收点独立一行 `- [ ] 名称：简短规则或数值。`；不再拆成“系统功能”和“数值”两份清单。
- 只保留公式、血量、攻击力、等级、收益、消耗、概率、容量，以及道具获取与使用、付费价格与奖励等规则。
- 一项只描述一个可独立确认的规则，不把整个系统塞进一个复选项，不附长段解释或嵌套步骤。
- 不记录动画、音效、特效、UI 样式、加载等表现验收，也不堆叠技术实现、修改历史、日期、编译日志和测试过程。
- 数值写清单位，公式说明必要变量；长配置表使用简短链接，不复制整份配置或逐段展开曲线。

示例：

- [ ] 关卡石头血量：按当前关卡血量表配置。
- [ ] 等级攻击力：向下取整（10 × 1.1^等级）。
- [ ] 测试球使用：每次消耗 1 个，每格最多 10 个。

示例仅说明格式，不作为目标项目已有功能或数值的依据。

## 更新流程

1. 读取现有清单及本次涉及的代码、配置和实际功能入口，只核对受影响的规则；用户要求全面整理时再盘点各系统。需要查询场景或 UI 节点时遵循工作区 Roblox MCP 规则。
2. 根据当前实现更新对应的单行条目；同一规则更新原项，新增规则才加项，已移除规则删除。未实现计划、占位入口和迁移的示例配置不列为可用功能；部分接入须简短注明范围。
3. 付费道具须确认实际商品映射、购买入口与发奖逻辑；没有接入时仅写一句现状，不将示例商品价格当成实际售价，也不创建虚假的待验收项。
4. 新项默认未勾选；公式、数值、使用或购买规则变更时，只取消受影响项及相关联项的勾选。纯排版与措辞整理保留原状态，范围不明确的项保持未勾选并简短注明。
5. 交付前检查每项是否独立、简短、可追溯至当前实现；删除重复项和表现细节，确认链接有效。

## 验收状态

- `- [ ]` 表示待确认；`- [x]` 只能由用户亲自勾选，或用户明确授权 AI 勾选指定项。测试通过不等于授权勾选。
- 规则改动取消勾选后，重新勾选仍需用户的新授权；不能用旧验收结果证明修改后的规则通过。
- 当前实现用于描述规则，不等于规则已符合用户预期；有设计要求时以用户确认的要求为验收依据。
- 只整理清单不代表完成实际验收。遵循工作区测试授权限制，编译或构建成功不代替玩法、存档或支付验收；验证结果在回复中简述，不塞进清单。
