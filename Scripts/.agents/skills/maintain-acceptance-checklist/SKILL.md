# 维护系统验收清单

维护 `Docs/功能验收清单.md`。它是系统验收清单，只记录已实现系统的关键功能和核心数值，不是修改日志或技术测试报告。

## 收录与更新

- 保留“系统功能验收清单”和“数值验收清单”两部分，各自以系统为验收单位；每个系统原则上各一项，用简短描述概括主流程、关键结果或核心数值，相关代码和配置链接按需提供。
- 只收录有实际功能入口的系统；未接入的配置、占位按钮和未来计划不列项。数值部分只写成长、奖励、消耗、概率、容量等核心规则，不罗列动画和表现参数。
- 新增、移除系统，或改变系统核心流程、玩法规则、核心数值时，更新原系统项，不为每次修改追加条目。
- 路径修正、节点改名、普通 bug 修复、UI 微调、动画特效细节、性能优化、日志及工具改动不写入清单，也不因这些修改自动取消勾选。恢复原有预期行为的修复不记录。
- 核心规则变化或发现原系统验收结论失效时，仅将受影响的系统功能项或数值项改回未勾选，必要时简短注明待验收的关键结果，不写修复过程。
- 先读现有清单，只按需核对相关实现、配置和入口；不因局部修改全面盘点项目。场景节点查询遵循工作区 Roblox MCP 规则。
- 整理时合并零散细项，删除修复历史、编译构建记录和实现细节，保留关键系统验收范围。

## 验收状态

- 新系统默认 `- [ ]`。只有用户亲自勾选，或明确授权 AI 勾选指定系统项时，才使用 `- [x]`。
- 预期来自用户要求或已确认的设计，不能仅凭现有实现推定正确。已发现关键功能不符合预期时，不保留通过状态。
- 用户要求记录验收结论时，在对应系统项写简短结果，必要时附日期或证据链接。部分功能通过不等于整个系统通过。
- 遵循工作区验证授权；编译、构建成功不代表系统验收通过。日常开发验证结果不写入清单。

## 完成检查

清单以系统为单位，只有关键功能和核心数值，无零散修复或未实现功能；未擅自勾选。仅整理文档时，不声称已完成实际系统验收。
