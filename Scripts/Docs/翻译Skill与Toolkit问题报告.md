# Roblox 翻译 Skill 与 StudioGameToolkit 问题报告

日期：2026-11-19  
范围：`roblox-translate` 全表审查、StudioGameToolkit「与云端对比」以及两者之间的导出交接。

## 结论

- **确实漏翻过：13 条、221 个空白单元格。** 好友加成、重生路线和战利品截图设置已被收进 CSV，但对应的 17 个语言列当时是空的。现在空白已补齐；另有 53 条、429 个与原文相同的非英语单元格，仍需判断哪些该翻、哪些应保留。
- **也有「发现了，但当轮没有翻完」的问题。** 显式调用 Skill 后，有一轮只审查并报告缺译；另一轮获得写入授权后，只先保存好友加成 85 格，重生引导等 136 格留到后续。需要分别处理调用方式、审查续接以及写入权限，不能把三个问题都归为翻译质量。
- **权限挡住的是落盘，不是翻译本身。** 正式文件在 `Scripts/` 外的 `GameKitWorkspace/Translation/`。可读不代表可写；工具可以先核查文案并准备译文，正式保存需要对应目录的写权限。
- **Toolkit 的云端复用结果需要独立核验。** 截图显示复用 0 条、0 个单元格；仅凭该截图无法区分云端快照确实没有可复用译文、条目匹配失败、快照或语言映射异常，还是统计显示与实际写入不一致。没有证据表明 Toolkit 删除了线上译文。

## 为什么会这样

这次先后卡在三个不同的环节。**Toolkit 收录并导出了 Source，但这批生成没有把缺的目标语言翻出来；Skill 找出了空白，但旧记录失效后没有及时接上独立的补译批次；最后，正式文件位于当前会话的可写目录之外，保存又需要单独放行。**

| 发生了什么 | 已确认的直接原因 | 还不能断定什么 |
| --- | --- | --- |
| Toolkit 显示收录完成，导出的 CSV 仍有 221 格空白 | 导出报告的 `complete: true` 和 725 条来源记录不代表译文填齐。生成说明写着「本地非空译文优先」；该批次实际记录复用 0 格。导出原件（用哈希确认）仍有 221 格空白，后续补译才把它们写进去。 | 对这 221 格而言，是云端本来没有译文，还是快照、身份匹配或语言映射导致没取到，需要逐格对照生成时的快照。 |
| 显式叫了 Skill，第一轮仍只给出缺译数字 | `report` 只读，只负责找问题；生成译文、审查、`apply` 保存是后续步骤。新导出的来源索引哈希与旧记录不符，旧记录在读入时就被拒绝。已有流程要求手工核对后迁移，没有可直接接续的步骤；该轮因此停在诊断，没有先把能独立确认的缺译另行处理。 | 索引冲突拦的是旧记录的直接续用，不证明新条目不能翻，也不证明旧译文全部作废。 |
| 准确报出「空白 0」，仍可能有文案没翻 | 机械检查只把空字符串或纯空白算作缺译。如果直接放入原文，参数和富文本通常也原样保留，会通过结构检查；语义复审尚未完成时，这类问题不能靠机械校验发现。 | 与 Source 相同的 429 格有多少确实不该保留，必须按语种、用途复核。 |
| 能查文件，不能保存；放行后也只先写了 85 格 | 正式 CSV 和审查 JSON 与 `Scripts/` 是并列目录下的文件，当前会话的工作区写权限不覆盖它们。只读诊断能做，正式落盘需要平台放行。获准后的可见交付只完成好友加成一批，剩余 136 格仍是后续工作。 | 没有证据表明后 136 格因第二次权限拒绝而留下；也不能把一次对话里的许可视为所有会话长期拥有目录写权限。 |

## 1. 确认漏翻：文案已经收录，17 个语言列却全空

| 当时确认缺译的范围 | 文案 | 空白单元格 |
| --- | ---: | ---: |
| 好友加成：当前加成、邀请按钮、规则、标题和规则正文 | 5 | 85 |
| 重生路线：赚钱、攒钱、买装备、买光环、训练场提示 | 5 | 85 |
| 战利品截图设置：按钮、参数说明和无效倍率提示 | 3 | 51 |
| 合计 | 13 | 221 |

这是**收录后未填译文**。过渡审查记录保存的原始 CSV 与 Toolkit 生成报告的 `generation.csvSha256` 一致，验证了这 221 个空白在 Toolkit 导出时就已存在。一轮补译只写了好友加成 85 格，所以接下来用户看到的 **136 个缺译**就是其余 8 条。随后，本地正式 CSV 与过渡记录最近保存的哈希一致，复核为 **725 条 × 17 个语言列，空白 0 个**。这证明上述空白已补齐，不能证明游戏客户端已显示译文、云端已更新或全表已审完。

## 2. 疑似漏翻：译文非空，但玩家可能仍看到原文

当前 CSV 中，排除英语列、纯参数和无字母文本后，有 **53 条文案、429 个非英语单元格与 Source 相同**。这组数据是待复核线索，不能和已确认的 221 个空白相加。

**复现：** 在一条英文 Source 的测试记录中，将日语译文填为同一句英文，保留原占位符和富文本，再做机械校验。现有 [mechanical 检查](../.agents/skills/roblox-translate/scripts/translation_review.py#L152) 将空白计为缺译，其余检查覆盖占位符和富文本；这种单元格可以通过机械校验。Skill 已要求逐语言语义复审，但现有机械报告不会专门提示这类嫌疑。

**影响：** 只看「空白为 0」容易漏掉仍显示英文的按钮和任务提示。反过来，像 `Aura` 在西语中可能就是正确译文；专名、符号和纯参数也可能应原样保留。

**建议和验收：** 在工作流中把「空白」「与原文相同、需确认」「语义未审」分别统计。优先展示有明确目标语言且整句仍与原文相同的操作提示，同时允许有证据地确认保留。用三类样例验收：空白译文报缺译；整句英文填入日语列会被提示复核；西语 `Aura` 经确认可保留，纯参数不会因与原文相同被误报。

## 3. 为什么有时「检查了但不翻」或「只翻一部分」

- **普通开发不会自动进入全表补译。** [Skill 入口](../.agents/skills/roblox-translate/SKILL.md) 要求显式调用，[调用配置](../.agents/skills/roblox-translate/agents/openai.yaml) 也关闭了隐式启用。正常开发和玩法查询可以只接入或说明 Source；这不等于 17 个语言列会自动得到译文。用户若直接说「帮我翻译这 136 格」，交互应让这条请求进入明确的补译流程，或马上说明需要怎么启用，不能把它当成单纯覆盖检查。
- **显式调用后也发生过只报告缺口。** 「审查 Roblox 全表翻译」已显式调用 Skill，却因旧记录无法续接，只报告 221 个空白，没有写回任何译文。之后另一会话得到写入授权，先保存 85 格，留下 136 格；该轮说明了哪些尚未完成，但不能算翻译任务完成。补译请求里，和旧结论迁移无关、来源已确认的新条目应能继续准备和分批处理。

### 审查记录无法直接续接

**复现：** 用现有 `translation-review.json` 运行 `report`，得到 `Context index changed; reconcile against a fresh review`。旧记录覆盖 716 条；对应当前 725 条 CSV 的 `translation-review-reconcile.json` 可正常读取，无输入冲突、无待应用译文，但仅记录 **221 / 12,325** 个单元格完成语义复审。旧记录的结论并未因此在新记录中自动生效。

**影响：** 拒绝拿旧记录直接写新 CSV 是正确的保护。缺口在于目前要手工核对和移交证据；仅重新建档会让已完成的工作无法直接续用，而整批复制完成标记又可能放过已经变化的条目。

**建议和验收：** 提供可预览的续接流程。按精确 Key，或无 Key 时按精确 Source＋Context，对齐身份；另核对 Source、来源证据及当前译文。预览分别列出可承接、需复核和冲突的条目，再建立新基线。用行重排、新条目、同 Key 改 Source 和译文改动做验收：行重排不会把证据移错，改动只让受影响的结论回到待审，历史待确认项不被静默丢弃。续接过程不覆盖正式 CSV。

## 4. 权限：可以读正式表，但不能直接保存

**实际经过：** 「检查新增功能的翻译覆盖」会话能读取正式 CSV、来源索引和旧记录，也定位了 13 条文案的来源。它指出当前会话的可写范围不含 `GameKitWorkspace/Translation/`，而 [Skill 的补译流程](../.agents/skills/roblox-translate/references/workflow.md) 要求「正式输入无写权限时请求权限，不用副本冒充交付」。因此该轮没有写回。用户随后回复「允许写入」，下一轮报告成功把好友加成 85 格写入正式 CSV。剩下的 136 格当时只是尚未补完，没有证据表明它们再次被权限拒绝。

| 动作 | 需要的权限或授权 |
| --- | --- |
| 读 CSV 和索引、查来源、生成并校验候选译文 | 读权限；可先在内存或临时目录完成，不必等待正式目录写权限 |
| 保存正式 CSV、保存或迁移同目录的审查记录 | 正式目录的写权限或平台批准的提权路径；用户要求补译也不能自动改变沙箱的可写范围 |
| 修改 Lua、UI 或配置，重新导出覆盖输入，上传 Roblox 云端 | 各自需要单独授权；本地补译和保存不包含这些操作 |

**建议和验收：** 补译开始时查清正式目录是否可写，并把权限问题与索引冲突分别记录；只读核查和候选翻译照常完成。需要权限时，在候选已可校验后说明准确路径和拟写文件，集中请求本次落盘所需的权限。获准后保存并重读正式文件，汇报本次实际落盘的数量；若未获准，标记「候选已完成／未写回」和具体原因，不能记作「已翻译并保存」。另对同一请求分别用只读和可写会话验证这两条路径。

## 5. StudioGameToolkit：云端复用为零，原因在界面上不可定位

**已观察到：** 用户截图中的「与云端对比」显示上传 CSV **725 条**，**新增 15、修改 710、未变更 0、待移除 3**，另显示「复用云端译文 0 条文案 · 0 个译文单元格」。截图中的 `Aura` 是无 Key 条目；`es-es`、`es-mx` 的字段差异是云端为空、上传 CSV 为 `Aura`。这解释了该条为什么会算「修改」，并不能证明这两个单元格原来有可复用译文，也不能解释所有 710 条修改。截图说明「待移除」是差异标记，线上是否删除取决于实际导入操作。

**同批次报告也写着复用 0。** [Toolkit 生成报告](../../GameKitWorkspace/Translation/translation-report.json) 的 `generation.cloudComparison` 与截图的 15／710／0／3 一致，且 `reusedEntries=0`、`reusedTranslations=0`。同一报告却有 `cloudReused=true`，并显示「已自动复用云端译文，本地非空译文优先」。因此至少可以确认：**成功式提示和实际复用数量没有区分开**；不能把这个布尔值当成至少复用了一个单元格的证据，也不能只把 0 归因于页面渲染。对于 710 条修改，本地非空优先可以解释部分字段为何和云端不同，但在没有逐项归因前，不能断言全部来自同一原因。

**排查建议：** 固定同一份生成时的云端快照、导出来源索引和上传 CSV。选取已知在快照中有非空译文的有 Key 和无 Key 条目，并加一个云端为空的对照条目。逐条比对身份（Key 或 Source＋Context）、语言列、快照值、生成后的 CSV 值，以及对比面板的复用计数。若快照里没有已知非空的正例，先确认绑定项目、快照是否取齐及语言是否被正确识别，不能用当前截图直接判定复用逻辑坏了。

| 对照结果 | 优先定位 |
| --- | --- |
| 快照中有非空译文，条目身份与语言都匹配，生成 CSV 却未保留该值 | 检查复用匹配和写入规则，查清是否有明确的覆盖条件 |
| 确认译文来自云端且写入 CSV，界面复用仍为 0 | 检查复用来源记录和界面统计 |
| 云端单元格为空，CSV 有本地补译 | 「修改／补充内容」可以成立，该单元格不应算云端复用 |

**验收：** 能用同一导出批次复算复用条数和单元格数，解释复用为零的原因。在界面能区分「云端没有可用译文」「有译文但无法匹配或未采用」「已复用」；差异列表仍可独立显示修改和待移除。
