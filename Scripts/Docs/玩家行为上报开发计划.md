# 玩家行为上报开发计划

编写日期：2026-10-19。状态：代码已实现，运行与正式后台验收待完成；实施结果见[玩家行为上报使用说明](玩家行为上报使用说明.md)。

审查前提：用户已确认游戏尚未发布，正式上线的玩家均从新档开始。上报随首次发布一同上线，不设计历史玩家补数、历史首付识别或旧档统计迁移。开发测试账号不进入正式统计；不因此删除任何已有测试存档。

## 1. 目标与范围

第一版只回答五个问题：

1. 新手引导到达第几步，是否全部完成。
2. 玩家本次在线多久，离开时引导停在哪一步。
3. 玩家买了哪个光环、哪把镐子。
4. 玩家用钻石买了什么、买多少、花多少。
5. 玩家用 Robux 买了什么、实际花多少；是否首次付费，首付前累计玩多久。

通用上报管理器放入 FX/FC/FS 框架，项目层负责业务事件及参数。使用 Roblox AnalyticsService，在 Creator Hub 查看汇总数据。次日、七日留存及平台收入优先使用 Roblox 原生报表。

不增加步骤耗时、按钮点击、商店浏览漏斗、逐玩家日志后台、外部分析服务。本轮仅编写本计划，不修改业务、框架、配置或验收结论。

## 3. Roblox 官方依据

本次通过浏览器实际读取以下官方页面；接口不使用过时的 `Fire*` 系列：

- [AnalyticsService API](https://create.roblox.com/docs/reference/engine/classes/AnalyticsService)
- [漏斗事件](https://create.roblox.com/docs/production/analytics/funnel-events)
- [经济事件](https://create.roblox.com/docs/production/analytics/economy-events)
- [自定义事件](https://create.roblox.com/docs/production/analytics/custom-events)
- [自定义字段](https://create.roblox.com/docs/production/analytics/custom-fields)
- [事件限制和 View Events 验证](https://create.roblox.com/docs/production/analytics/event-types)
- [MarketplaceService.ProcessReceipt](https://create.roblox.com/docs/reference/engine/classes/MarketplaceService#ProcessReceipt)

确认规则：

- 漏斗、经济、自定义事件只能由已发布游戏的服务端发送，客户端和 Studio 不能向这些报表发送事件。
- 新手使用 `LogOnboardingFunnelStepEvent(player, step, stepName, customFields)`。漏斗从 1 开始，同一玩家重复步骤只统计首次；跳过步骤会被平台自动补为完成。只根据权威引导状态上报，不根据客户端请求或玩家余额推断完成。
- 一次性引导不需要每次进服生成新的 funnelSessionId。漏斗超过 180 天无事件后，平台保存的步骤会过期。
- 经济使用 `LogEconomyEvent(player, flowType, currencyType, amount, endingBalance, transactionType, itemSku, customFields)`。Source/Sink 均传正数金额，余额为交易后余额且不小于 0，transactionType 传枚举的 `.Name`。
- 自定义使用 `LogCustomEvent(player, eventName, value, customFields)`；一个事件只有一个数值 value，报表支持次数、独立人数、平均值、总和、最小值、最大值等聚合，不是任意 JSON 查询。
- 每个事件最多 3 个自定义字段，键使用 `Enum.AnalyticsCustomFieldKeys.CustomField01/02/03.Name`，值必须是字符串。不要把 UserId、PurchaseId、时间戳、会话 GUID 当作报表维度。
- 官方限流表给出的总请求上限为每分钟 `120 + 20 × CCU`；自定义事件名最多 100，漏斗最多 10，每漏斗最多 100 步。字段组合过多会归入 Other。
- 官方经济资源类型上限存在文档差异：API 页写 5，事件限制页写 10。第一版仅使用 Money、Diamonds 两种，不依赖较大的限制；实施时再次核实。SKU 超过 100、交易类型超过 20 会遇到限制或 Other 聚合，不为每次购买生成新 SKU。
- 图表通常需要约 24 小时生成；可在对应页面的 View Events 检查近期事件。代码调用无异常不等于后台已经入库。
- ProcessReceipt 的 `PurchaseId` 是购买唯一标识，`CurrencySpent` 是实际 Robux 支出。回调可能重试、并发跨服、乱序；旧收据确认成功也可能再次回调。不得以客户端购买完成事件、配置标价或当前商品价格代替真实收据。

## 4. 分层与文件方案

### 框架层：FS.AnalyticsManager

新增 `ReplicatedStorage/Scripts/Framework/Server/Modules/FSAnalyticsManager.luau`，由 FServer 加载并初始化。名称为拟定，实施时遵循现有模块注册风格。

职责限定为：

- 封装本次所需的新手漏斗、经济事件、自定义事件三个官方接口。
- 参数边界校验、统一字段转换、Studio 禁止真实发送、错误隔离与有限诊断。
- 上报失败不能中断引导、扣款、发奖、存档或改变收据决定。
- 控制事件数量，避免逐帧或每秒发送；不建设持久队列、无限重试或外部 HTTP 系统。

框架不引用 Game 配置，不写死光环、镐子、钻石商品、新手步骤及首付规则；不把 Roblox Player 与框架玩家对象混用。三个封装均接收明确的 Player 和已结算参数，返回值只能表示本地校验/调用结果，不能命名为“入库成功”。

### 项目层

拟新增服务端 `SAnalyticsCompClass.luau` 管理每玩家会话状态，必要时新增小型事件定义模块集中管理稳定名称和字段槽位。只有重复逻辑确有需要才拆分服务，不为每类事件建立一个类。

- 在项目玩家对象注册组件，使用现有生命周期与每秒更新机制，不添加新执行入口。
- 在业务成功结算点调用项目组件，组件再调用框架管理器。
- 在 PlayerDataConfig 定义必要的私有持久字段和新档默认值；首次发布无需新增历史统计迁移分支。不直接操作生成配置文件。
- 框架收据服务如需提供“本次新结算且保存成功”的结果/钩子，只增加通用契约，不嵌入项目商品和首付逻辑。

## 5. 事件口径

下表为拟定契约，实施时锁定后不随意改含义。所有数值使用原始数值，不使用 NumberToText 格式化结果。

| 事件 | 类型及 value | 三个字段槽位或固定参数 | 触发点 |
| --- | --- | --- | --- |
| 主新手进度 | Onboarding，步骤 1–9 | 稳定英文步骤名；保留版本标识槽位 | 开始主引导到达步骤 1；每次服务端推进记录新到达步骤；全部完成为第 9 个终点 |
| `SessionStarted` | Custom，1 | 引导版本、FirstSession/ReturningSession、统计版本 | 项目玩家读档和登录完成后，每会话一次 |
| `SessionEndedDuration` | Custom，本次在线秒数 | 主引导阶段、FirstSession/ReturningSession、统计版本 | 玩家对象清理前捕获快照，每会话至多一次 |
| 光环购买 | Economy Sink | Money、实际扣款、交易后余额、Shop、`Aura:<AuraId>` | Buy 结算成功并提交装备数据后 |
| 镐子购买 | Economy Sink | Money、实际扣款、交易后余额、Shop、`Weapon:<ToolId>` | Buy 结算成功并提交装备数据后 |
| 钻石购买 | Economy Sink | Diamonds、实际扣款、交易后余额、Shop、`GemGoods:<goodsId>` | 钻石商店完整结算成功后 |
| `RobuxPurchase` | Custom，receipt.CurrencySpent | 稳定商品 ID、商品类别、首付分类 | 新购买完成发奖并保存成功后 |
| `FirstPurchasePlaytime` | Custom，累计在线秒数 | 稳定商品 ID、OnlineSinceFirstLogin、统计版本 | 首次成功结算的 Robux 购买，每玩家一次 |

补充约定：

- “新手做到第几步”统一为当前到达/正在进行的步骤，不等同于已完成该步。第 9 点仅代表 8 步主引导全部完成，不再创建步骤开始和完成两套事件。
- 第 6–8 步是系统计时提醒，在文档和报表名称中保留该含义，不视为主动操作成果。光环独立引导不硬拼到主漏斗，因为它不保证与主引导严格连续；第一版以光环购买事件观察该玩法。
- 引导完成后代码中的 stepIndex 为 0，离服字段必须写 Completed；未开始写 NotStarted，不能都归为 Step0。
- 所有玩家上线时都是新档，但仍需区分第一次会话与之后的回访会话，以免把老会话的离开情况混进首局体验。使用私有持久的“已开始首局”标记；不增加 New / Existing / Unknown 历史兼容分支。会话时长定义为项目登录完成至离服快照的服务器在线秒数，包含挂机，不含加载前时间。
- 首版不额外增加在线分钟里程碑。无法捕获的进程崩溃、断电、离服发送失败会造成离服样本缺失；将自定义离服时长用于分组观察，平台整体时长使用原生参与度报表，不能声称完全无漏。
- 购买是否发生可由独立购买人数和事件次数判断，不另报“有没有买过”。免费默认镐子、奖励解锁、装备/卸下、购买失败均不算付费购买；0 成本若存在，需要单独判定，不向 Economy 发送 0 金额。
- 钻石目前每次请求购买一个商品包；交易次数与包内奖励数量不同。SKU 对应稳定商品，数量/奖励含义记入商品映射表；若核对后发现可变数量商品，另定一个数值事件记录数量，不假装经济事件自带 quantity 参数。
- 同一交易只记一次货币 Sink，不在通用扣款层和商店业务层双重发送。首版只覆盖所列商店的消费，不据此宣称经济收支完整或用它评估完整净产出。
- Robux 是真实支付，自定义付费事件不是把 Robux 伪装成玩家钱包货币。购买钻石所得 Diamonds 如需记录 IAP Source，只能在收据保存成功后，以实际到账量和正确时点余额发送，不能在 BuyHandler 的可回滚过程里提前发送。

## 6. 去重、计时及准确性边界

### 新手

- 使用平台一次性漏斗去重，进服不创建新漏斗；同一会话不重复发送未变化进度。
- 全部正式新档从主引导第一步接入，不新增旧档入组资格和补数流程。初始化会话后、发布 Tutorial.Login 前确保项目上报组件可用，防止漏掉第一步。
- 主引导任意推进都应由统一的权威状态变化点捕获，包括服务端计时推进，不只监听客户端动作。项目子类接入即可，不为埋点重写框架引导流程。
- Studio 默认不发送；已发布测试环境中的开发账号也通过服务端统计开关排除。GM 重置不能让测试账号污染正式漏斗，不清库、不清除平台统计。

### 会话与累计在线

- 以同一服务端时钟计算实际经过时间，不用“每秒回调一次就加 1”。登录完成记录起点；每次更新提交距上次记账的增量，离服补齐尾差，避免卡顿误差和重复累计。
- TrainingPlaytime 为累计已记账秒数；读取首付时长前补记本会话尚未累计的部分，不能把完整本次时长再加到已经包含本会话的累计值上。
- 首局标记、累计在线沿用玩家档案自动保存和离服保存；不为每秒计时额外执行 DataStore 保存。清理前结束一次，析构重复调用不重复记账。
- 不依赖组件遍历顺序：会话起点在玩家登录完成的明确位置建立，离服快照在业务组件清理前取得。新手第一步与 SessionStarted 也需在该顺序下明确触发。
- 累计在线精确到本次已观察的服务器时间。服务器进程异常终止可能丢失最后一次成功存档后的增量，正常离服测试通过不能推断崩溃场景无损。

### 支付与首付

- 不能简单在 `decision == PurchaseGranted` 后上报，因为历史收据同样返回 PurchaseGranted。
- 在现有收据串行与会话锁保护中，区分新收据、保存重试、历史已确认收据；奖励、首付标记及所需上报元数据与同一档案保存，保存成功后才执行分析副作用。
- 新档首付状态默认为未付费。第一次新收据结算时确定首付，后续购买为复购；不新增历史付费分类或历史首付推断。
- 官方收据不提供交易发生时间，多个待处理收据回调顺序不确定。因此首付商品严格定义为本系统首次成功结算的购买，时长为结算时累计在线，不声称还原真实付款时间顺序。
- 在第一次发奖时、保存之前捕获首付商品与累计在线秒数，并随收据状态持久化；保存失败后重试复用该快照，不按重试时刻重算首付时长。
- 第一次保存失败时，当前实现已在内存写入 PurchaseReceipts。实施必须保留这笔尚未完成持久化的分析元数据；不能仅在 receipts 中没有 PurchaseId 时触发，否则保存重试成功后会漏掉整笔支付及首付事件。
- 首付持久状态、收据上报去重使用同一份权威记录，不维护相互独立的“已首付”布尔值；保存成功后先取得结果快照，再执行受保护的分析调用。不要在释放购买串行锁后重新读取可能已经被下一笔购买改变的首付状态。
- AnalyticsService 与 DataStore 没有本项目可用的跨服务原子提交。持久标记后崩溃可能漏发，先发送再持久化可能重发；第一版在原有收据保存中一并记录“已安排尝试上报”，保存成功后每笔最多尝试发送一次。平台调用失败不重置标记，不追加保存，不重试支付来重试分析；接受漏报，不承诺 exactly-once。
- 报表收入以 Roblox Monetization 为准，自定义事件用于商品和首付行为分析，不作为财务账本。

## 7. 开发顺序与完成条件

2026-10-19 实施更新：六阶段代码与交付说明已落地；以下勾选保留为完整验证条件，不以代码保存或同步代替运行、故障重试及后台验收。历史“本轮仅编写计划”等描述为编写计划时的范围记录，本次实施由用户后续请求授权。

- [ ] **一：补齐接入审查。** 列出每个商品 ID/币种/成功点；检查 Ready/离服/关服顺序，明确累计在线接入和收据保存重试状态，确认当前 Studio 目标。完成条件：事件都有真实数据来源，没有未知参数被默认猜成有效值。
- [ ] **二：实现框架管理器。** 只封装三个已核实接口及错误隔离；初始化一次。完成条件：项目无关，Studio 不真实发送，上报失败不影响业务。
- [ ] **三：接新手与会话。** 全新档主漏斗、阶段快照、首局/回访标记、累计在线计时、开始/离开事件、组件清理幂等。完成条件：重登不新增一条新手漏斗，完成状态不误记为未开始；首局与回访可区分，在线不重计，正常离服/关服不重复结束。
- [ ] **四：接装备及钻石购买。** 在三个业务结算点发送对应 Sink，固定 SKU 映射。完成条件：成功一次记一次，失败/装备/默认奖励不记消费，金额和余额与服务端结算一致。
- [ ] **五：接 Robux 和首付。** 完成新收据成功契约、保存失败重试快照、首付标记/时长及去重。完成条件：保存失败不记成功，之后保存成功能产生一次事件；已处理收据重放不增加购买数，重进不重复首付，分析异常不改变发奖及 receipt 决定。

## 8. 验证与发布检查
